# The MiniLedger schema

Phase 1 deliverable: what each table is, why it exists, and which invariants
the database enforces on its own.

## The model in one paragraph

Money never changes amount, it only changes location. Every movement is
recorded as a **transfer**, and every transfer writes at least two **ledger
entries** — one debit, one credit — whose signed amounts sum to exactly zero.
The entry log is append-only and is the sole source of truth. Any balance you
are ever shown is a `SUM` over that log, or a cached total that a reconciliation
job independently re-derives from that log and refuses to let drift.

---

## `accounts`

**What it is:** every place money can sit. Customer wallets and internal house
accounts live in the same table.

**Why it exists as one table:** there is no separate "user balance" concept. A
customer wallet is a *liability* account — the money is theirs, we are merely
holding it — and the house accounts that fund it are equity or asset accounts.
Keeping them together is what makes the zero-sum invariant checkable across the
whole system: if wallets lived somewhere else, you could never ask "does the
entire ledger balance?"

| Column | Why |
|---|---|
| `id` | UUID, `gen_random_uuid()`. No meaning, no sequence to leak volume. |
| `name` | Unique human handle (`wallet:alice`) so seeds and tests never hardcode a UUID. |
| `account_type` | One of asset / liability / equity / revenue / expense, CHECK-constrained. |
| `normal_balance` | **Generated by the database** from `account_type`. |
| `currency` | Present and CHECK-pinned to `USD`. |
| `allow_negative_balance` | Whether this account may go below zero. |
| `created_at` | `timestamptz`, server-side `now()`. |

`normal_balance` is a `STORED` generated column, not an application-written
one. A column no code path writes is a column no code path can write wrongly —
the debit/credit convention physically cannot drift from the account type.
Postgres rejects an `UPDATE` against it outright.

`allow_negative_balance` is a per-account flag rather than a hardcoded rule like
"liabilities can't overdraw", because the rule is then *data you can inspect*
instead of *logic you have to go and read*. The float account is allowed to go
negative; customer wallets are not.

`currency` exists even though MiniLedger is single-currency on purpose. Pinning
it with a `CHECK` makes the scope decision enforced rather than merely
documented, and isolates it: the day multi-currency lands, one `CHECK` is
dropped and the composite foreign keys below start doing real work.

## `transfers`

**What it is:** one business-level movement — "move $50 from the float to
Alice's wallet". One row per intent.

**Why it is separate from the entries:** the intent is a single fact with a
single idempotency key. The effect is two or more rows that must balance. They
change for different reasons and are written at different grains, so they are
different tables. Phase 2's idempotency key points at a transfer, not at an
entry.

**The direction rule, stated once:**

> **The source account is DEBITED. The destination account is CREDITED.**

What that does to a balance depends on the account's normal direction — see the
worked example below. Enforced here:

- `amount > 0`. Direction is expressed by *which account is which*, never by the
  sign of the amount. A zero amount is almost always an uninitialised variable,
  and a negative one would let a transfer run backwards past the overdraft check.
- `source_account_id <> destination_account_id`. A self-transfer is a no-op that
  still writes two entries and pollutes the log.
- Composite foreign keys on `(account_id, currency)` → `accounts(id, currency)`,
  for both sides. This is why `accounts` carries a redundant-looking
  `UNIQUE (id, currency)`: it is the composite target. The effect is that the
  **database** guarantees a transfer's currency matches both of its accounts,
  rather than that being an application check somebody eventually forgets.

## `ledger_entries`

**What it is:** the append-only log of postings. One row = one single-sided
fact: "account X was debited 500". **This is the source of truth for every
balance in the system.**

| Column | Why |
|---|---|
| `id` | `BIGSERIAL`. Entries form an ordered log; a monotonic id gives cheap ordering and a natural high-water mark. |
| `transfer_id` | Which movement this posting belongs to. |
| `account_id` | Which account it hits. |
| `direction` | `debit` or `credit`. |
| `amount` | Always **positive**. Direction carries the meaning. |
| `signed_amount` | **Generated**: `credit → +amount`, `debit → -amount`. |

Positive amounts plus an explicit direction is the standard accounting
representation, and it removes a whole class of sign bug: there is no way to
write a "negative credit" that quietly behaves like a debit.

`signed_amount` exists so the balancing invariant is a one-liner —
`SUM(signed_amount) = 0` per transfer — without the application ever computing a
sign. Credits are positive by convention; converting that into an account's own
direction happens in exactly one function, `balance_of()` in `app/ledger.py`.

Every foreign key is `ON DELETE RESTRICT`. Deleting a transfer must never
silently delete the postings that prove what happened. If a transfer needs
undoing, the answer is a **compensating reversal transfer**, never a `DELETE`.

## `account_balances`

**What it is:** a cache of each account's posted totals. **Not** the source of
truth.

Summing a log that grows forever gets slower forever, so posted totals are
maintained incrementally inside the same database transaction that writes the
entries (Phase 2). That trade is only safe because of Phase 3: `reconcile.py`
independently recomputes these totals from `ledger_entries` and fails loudly on
any mismatch.

> The cache is allowed to be wrong. It is not allowed to be wrong *silently*.

Debits and credits are stored as **two separate running totals** rather than one
net figure, for two concrete reasons:

1. Both counters only ever increase, so `>= 0` is a real `CHECK` the database
   can enforce. A single net column could not be constrained at all.
2. When reconciliation finds drift, knowing *which side* is wrong narrows the
   search immediately.

`entry_count` catches drift that happens to net out to the right number but is
built from the wrong set of entries. `last_entry_id` records how far the cache
has folded in, which turns "the cache is wrong" into "the cache is wrong and
here is where to start looking".

## The sign convention, worked

Alice's wallet is `liability` → credit-normal. The float is `equity` →
credit-normal. House cash is `asset` → debit-normal.

**Funding Alice with $50** (`source = house:float`, `destination = wallet:alice`):

| account | direction | amount | `signed_amount` |
|---|---|---|---|
| `house:float` | debit | 5000 | −5000 |
| `wallet:alice` | credit | 5000 | +5000 |
| | | | **0** ✅ |

Balances, each in its own normal direction:

- `wallet:alice` is credit-normal → `credits − debits` = `5000 − 0` = **+5000**.
  Alice holds $50.
- `house:float` is credit-normal → `credits − debits` = `0 − 5000` = **−5000**.
  The float is $50 in the hole, correctly: we handed out money we did not take in.

Now the same two rows against a **debit-normal** account. A real deposit debits
house cash and credits the wallet:

- `house:cash` is debit-normal → `debits − credits` = `5000 − 0` = **+5000**.

Identical rows, opposite reading, purely because the account type differs. That
is not a special case — it is what debit and credit mean. Only `balance_of()`
needs to know.

Note that **balances do not sum to zero** — they are signed per account
direction. The raw `signed_amount` column does, across every entry ever written:

```sql
SELECT SUM(signed_amount) FROM ledger_entries;  -- must always be 0
```

## Where each invariant is enforced

| Invariant | Enforced by | Can app code bypass it? |
|---|---|---|
| Amounts are positive | `CHECK` | No |
| Direction is `debit`/`credit` | `CHECK` | No |
| Account type is known | `CHECK` | No |
| `normal_balance` matches account type | Generated column | No |
| `signed_amount` matches direction | Generated column | No |
| Transfer currency matches both accounts | Composite `FOREIGN KEY` | No |
| No self-transfers | `CHECK` | No |
| Every transfer has ≥ 2 entries | Deferred constraint trigger | No |
| Every transfer sums to zero | Deferred constraint trigger | No |
| Entries are never edited or deleted | `BEFORE UPDATE/DELETE` trigger | No |
| Transfers are never edited or deleted | `BEFORE UPDATE/DELETE` trigger | No |
| Balance cache matches the log | **Nothing** — audited by Phase 3 | **Yes** |
| No overdraft on a restricted account | Application (Phase 2) | Yes |

The last two rows are the honest part. They are cross-row, time-of-check
conditions that a constraint cannot express, which is precisely why
reconciliation exists.

### Why the balancing check has to be deferred

A transfer writes its legs as separate rows. After the first leg, the sum is
deliberately non-zero. A normal `AFTER INSERT` trigger would fire right then and
reject every legitimate transfer.

`DEFERRABLE INITIALLY DEFERRED` queues the check until `COMMIT`, by which point
both legs are present. The practical consequence, which the tests assert: the
`INSERT` succeeds and the error surfaces at `COMMIT`.

### One known gap

`TRUNCATE` does not fire row-level triggers, so it can still clear the log. The
test fixture relies on exactly that. In production the application role would
hold `INSERT` and `SELECT` only, with no `TRUNCATE` grant — see the README's
"What I deliberately left out".

## Migrations

| Revision | What it does |
|---|---|
| `0001_create_core_ledger_tables` | The four tables, plus every constraint SQLAlchemy can express declaratively. |
| `0002_enforce_append_only_and_balanced_` | The two invariants it cannot: append-only enforcement, and the deferred balancing trigger. |

Split this way because a `CHECK` sees one row at a time and cannot forbid an
operation. Everything in 0002 is necessarily procedural.

cp .env.example .env
